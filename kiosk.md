Project value

## Help customers order without needing staff to explain the interface.

### What the design needed to achieve

- ✓

Reuse one menu structure across kiosk, mobile, and web.

- ✓

Keep ordering readable through high contrast and clear controls.

- ✓

Give customers clear recovery steps when hardware or payment fails.

Problem

### The interface stands alone.

Each state must explain the next action because staff guidance is not always available.

Risk

### Small failures can stop an order.

Unclear prompts, physical input, and hardware faults can block checkout.

Direction

### Make feedback part of the system.

Shared rules connect readable screens, tested controls, and guided recovery.

Design decisions

## Connect channel rules, accessibility, testing, and recovery.

01

### Design the menu once

Shared structure

Backoffice defines item groups and menu tiles. The same structure supports kiosk, mobile, and web ordering.

Intended impact

Teams configure one menu while each channel keeps suitable interaction rules.

02

### Make readability a system rule

Accessible ordering

The high-contrast theme replaces local menu colours through the existing theme switch.

Intended impact

Customers can read and complete the full ordering journey in high contrast.

03

### Test controls on the hardware

Real conditions

We refined eight quantity selectors, printed them, and tested them on the kiosk before choosing one.

Intended impact

The selected control reflects real distance, scale, and touch conditions.

04

### Guide hardware recovery

Clear next steps

The scale flow now covers placing food, lifting it, holding still, capture, and temporary or persistent faults.

Intended impact

Customers can recover without guessing what the kiosk expects.
